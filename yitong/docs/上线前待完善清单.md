## 一、🔴 代码层红线缺陷（凭证配齐也跑不通，必须改代码）

### R1. 表白墙帖子举报断链 —— 举报入库但取不出、无反馈
- **位置**：`apps/server/src/modules/confession/confession.service.ts:673-684` `reportPost`
- **问题**：方法签名接收 `uid`，但方法体内完全未使用；`moderationRecord.create` 的 data 仅写 `targetType/targetId/reason`，不写 `reporterId`。
- **对比**：同模块 `treehole.reportGroup`（treehole.service.ts:651-660）写 `reporterId: anonId`，`job.report`（job.service.ts:289-296）写 `reporterId: uid`，唯独表白墙帖子举报漏写。
- **影响链**：
  1. `admin.listReports`（admin.service.ts:195）过滤 `reporterId: { not: null }` → 表白墙帖子举报在管理端专属举报队列**不可见**；
  2. `admin.resolveReport`（admin.service.ts:288）通知举报人时 `if (record.reporterId)` 为 false → 举报人**永远收不到处理结果通知**；
  3. 举报入库了但提取不出来、反馈闭环断裂。
- **修复方向**：`reportPost` 的 `moderationRecord.create` data 补 `reporterId: uid`。
- ✅ 已修复（feat/prod-闭环修复，2026-08-04）-- `confession.service.ts:681` 补 `reporterId: uid`；详见改动记录 2026-08-04 条目。

### R2. 编辑带图帖子必失败 —— 作者改自己帖子的闭环断裂
- **位置**：`apps/user-miniprogram/pages/post-create/index.ts:295` + `apps/user-miniprogram/services/upload.ts:13`
- **问题**：编辑模式下 `this.data.images` 是**已上传的 URL**（onLoad:102 从 draft 回填），`submit()` 在 `images.length > 0` 时仍调 `uploadImages(this.data.images)`；`uploadImages` 对每个 path 调 `wx.uploadFile({ filePath })`，而 `filePath` 必须是本地临时路径，传 URL 必 fail → `editPost` 不执行。**只改文字也炸**。
- **次生问题**：即使上传侥幸成功，316 行 `finalImages = [...this.data.images, ...imageUrls]` 还会把旧 URL + 重传 URL 拼重复。
- **修复方向**：`uploadImages` 区分「本地临时路径」与「已是 http URL」，对 URL 直接透传不再上传；或 `submit()` 编辑模式直接用原 images 数组。
- ✅ 已修复（feat/prod-闭环修复，2026-08-04）-- post-create 加 `originalImages` 身份判别（URL 透传 / 本地路径上传），删 finalImages 重复拼接；待微信开发者工具实测。

### R3. 活动专题列表跳转断链 —— 点不进详情
- **位置**：`apps/user-miniprogram/pages/confession/activity/index.ts:35`
- **问题**：`wx.navigateTo({ url: '/pages/confession/activity/detail?id=...' })`，但 `app.json` 注册的是 `pages/confession/activity-detail/index`（连字符，非斜杠）→ `navigateTo:fail url not in app.json`。
- **对比**：同目录 `topic/index.ts:35` 用的是正确路径 `/pages/confession/topic-detail/index`。
- **修复方向**：改为 `/pages/confession/activity-detail/index?id=${id}`。
- ✅ 已修复（feat/prod-闭环修复，2026-08-04）-- `activity/index.ts:35` 路径已改；待微信开发者工具实测。

### R4. 岗位审核闭环缺失 —— 管理员无法直接下架岗位
- **位置**：后端 `apps/server/src/modules/admin/admin.controller.ts`（无 `job-posts/:id/takedown` 路由）+ 前端 review panel（无岗位 sub-tab）
- **问题**：岗位由商家自助发布即 `PUBLISHED`，后端仅有 `POST admin/job-posts/:id/feature`（精品 toggle）和 `GET admin/job-posts`，**无下架/审核接口**；管理端 review panel 5 个 sub-tab 为「商家入驻/表白墙帖/树洞帖/评论/举报处理」，无岗位审核入口。管理员只能经举报间接下架（`resolveReport(takedown=true)` 走 `job_post` 分支，admin.service.ts:308-330）。
- **影响**：岗位内容审核无直接闭环；若岗位违规但无人举报，管理员无法主动处置。
- **修复方向**（需确认产品范围）：补 `POST /admin/job-posts/:id/takedown` 路由 + service + review panel 岗位 sub-tab；或确认「岗位免审核、仅举报驱动」为产品决策则标注接受。
- ✅ 已修复（feat/prod-闭环修复，2026-08-04，产品定「补完整下架闭环」）-- `admin.controller` 加 takedown 路由 + `admin.service.takedownJobPost`（TAKEN_DOWN+留痕+通知商家）+ review 岗位 sub-tab。

### R5. 商家审核队列 userNickname 恒空 —— 显示死数据
- **位置**：`apps/server/src/modules/admin/admin.service.ts:40` `getQueue()` + `apps/user-miniprogram/components/admin-panels/review/index.wxml:18`
- **问题**：`getQueue()` 映射商家时硬编码 `userNickname: ''`（未 join User 表），前端 WXML 渲染 `{{item.userNickname}}` → 每张商家卡片副标题空白。VO 类型声明为 `string`（services/admin.ts:11）但后端永不填充真实值。
- **修复方向**：`getQueue` 查询补 `include: { user: { select: { nickname: true } } }`，映射时填 `userNickname: m.user.nickname`。
- ✅ 已修复（feat/prod-闭环修复，2026-08-04）-- Merchant 模型无 user relation（清单假设有误），改单独查 User 昵称映射；`admin.service.ts` getQueue。

## 二、🟠 prod 部署前置凭证（非代码缺陷，填 env 即通）

代码层 dev/prod 分支切分符合 AGENTS.md §8 约定（dev mock / prod 抛 90003 阻断，不静默 mock）。**prod 上线前 `.env` 必须填实**，否则对应功能阻断：

| env 变量 | 用途 | 缺失时 prod 行为 |
|---|---|---|
| `JWT_SECRET` | JWT 签名（登录/refresh/ws 鉴权） | 🔴 **启动崩溃**，服务起不来（auth.module.ts:18-20，当前是占位 `change-me-in-prod`） |
| `WX_USER_APPID` | 微信小程序 AppID（登录/内容安全/支付/订阅共用） | 登录断(10004) + 内容安全断(90003) + 支付断 + 订阅消息失败 |
| `WX_USER_SECRET` | 微信小程序 Secret（code2session + access_token） | 同上 |
| `WX_PAY_MCH_ID` | 微信支付商户号 | 支付下单断(90003)（isReady=false） |
| `WX_PAY_API_V3_KEY` | APIv3 密钥（32 位，AES-256-GCM 解密回调用） | 支付下单断(90003)（isReady=false）← 当前缺失 |
| `WX_PAY_PRIVATE_KEY` | 商户 API 私钥（apiclient_key.pem 内容；多行用 \n 转义；亦可填 WX_PAY_PRIVATE_KEY_PATH） | 支付下单断(90003) |
| `WX_PAY_MCH_SERIAL_NO` | 商户证书序列号（请求头 Wechatpay-Serial） | 支付下单断(90003) |
| `WX_PAY_PLATFORM_PUBLIC_KEY` | 微信支付平台公钥（回调验签用） | 支付下单断(90003) |
| `WX_PAY_NOTIFY_URL` | 支付回调地址 | 凭证齐全时回调进不来，订单卡 PENDING（需公网 https） |
| `WX_PAY_REFUND_NOTIFY_URL` | 退款回调地址 | 真实退款走 V3 接口，回调验签需该地址（缺则退款不入账） |
| `MINIO_ENDPOINT` | 对象存储地址 | 全站上传断(90003)（头像/帖图/语音/资质/视频） |
| `MINIO_ACCESS_KEY` | MinIO 访问密钥 | 上传断(90003) |
| `MINIO_SECRET_KEY` | MinIO 密钥 | 上传断(90003) |
| `CHAT_WS_URL` | 自建 WS 聊天地址 | 默认 `ws://localhost:3001`，**需改公网地址**否则前端连不上聊天 |
| `MODE` | dev/prod 角色校验开关 | 漏配则 admin 登录校验被绕过（安全降级，建议同时设 `NODE_ENV=production` + `MODE=prod`） |
| `WX_SUBSCRIBE_JOB_APPLY_TEMPLATE_ID` | 报名提醒订阅模板 | 缺失只跳过，不阻断（站内通知 DB 入库不受影响） |
| `WX_SUBSCRIBE_JOB_STATUS_TEMPLATE_ID` | 报名状态订阅模板 | 同上，不阻断 |

> 注：聊天已改为**自建 WebSocket**（`im.service.ts` + `chat.gateway.ts`），不依赖腾讯云 IM 凭证，prod 实时聊天可用，唯一前提是 `CHAT_WS_URL` 配公网可达地址。

## 五、审查结论

**整体代码质量较高**：
- 18 个后端模块写操作全走 Prisma 持久化，无硬编码假数据返回；
- 读操作均真查库，状态机（报名/支付/匹配/工单）转换接口齐全且落库；
- 计数冗余字段（likeCount/followerCount/memberCount/unreadCount）均在事务内同步；
- 三端 shell 化后 panel 均真实取数渲染，无一处「敬请期待」占位、无 `console.log` 死处理；
- navigateTo 目标除 R3 外全部合法；前端 API 调用除岗位下架外在后端路由清单都能找到对应接口（无 404 断链）；
- 聊天已脱离腾讯云 IM 改自建 WS，prod 实时聊天可用且闭环（入库 + 在线推送 + 离线历史）。

**真正卡 prod 闭环的代码缺陷是第一节 5 项红线**：
- R1（举报断链）、R2（编辑带图帖）、R3（活动跳转）、R5（商家昵称空）是明确的 bug 或遗漏，改动小；
- R4（岗位审核）是功能缺口，需先确认产品范围再决定是否补。

**prod 上线前必须完成的动作**：
1. 修复 R1/R2/R3/R5（R4 视产品决策）；
2. 填实第二节凭证清单（尤其 `JWT_SECRET`、`WX_USER_SECRET`、`MINIO_*`、`CHAT_WS_URL`、`MODE=prod`，`WX_PAY_API_V3_KEY` + `WX_PAY_PRIVATE_KEY` + `WX_PAY_MCH_SERIAL_NO` + `WX_PAY_PLATFORM_PUBLIC_KEY` 已知缺）；
3. 第三节有意搁置项按产品需求决定是否补做。
