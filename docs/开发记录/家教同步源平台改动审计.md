## 接口契约

- 新增 `GET /internal/sync/tutor-demands`，路由目标为 `Demand/syncTutorDemands`。
- 请求必须携带 `X-Sync-Token`。源平台读取 `TUTOR_SYNC_TOKEN` 并通过 `hash_equals` 校验；未配置返回 503，鉴权失败返回 403。
- 返回 `version=1`、`mode=full`、`complete=true`、`itemCount`、`generatedAt` 和 `items`，供燚桐执行完整快照对账。
- 单条需求只输出展示字段及 `status`、兼容字段 `is_hide/is_refund`、`create_time`，不输出家长姓名、手机号等个人联系方式。生产表字段映射为 `price AS expense`、`trial_time AS teach_time`。
- 已核对生产 `cd_demand` 的 `SHOW COLUMNS`：该表没有独立 `is_hide/is_refund` 列，旧控制器对这两个字段的读写属于与生产 schema 不一致的遗留代码；可工作的退款/关闭路径会将 `status` 改为非启用值。因此当前生产接口以 `status` 表达生命周期，并将兼容字段固定为 0，不能把不存在的列直接加入查询。
- 仅 `status=1 && is_hide=0 && is_refund=0` 视为启用；其他状态或从完整快照中消失均由燚桐统一下架。若将来生产库正式新增独立隐藏/退款列，需同步调整接口字段映射与契约指纹。
- 燚桐不对同步内容调用微信内容审核，源字段经格式和生命周期校验后直接适配为兼职岗位。

## 目标侧对账

- 定时任务固定每 5 分钟执行；事务外一次拉取包含 `itemCount` 的完整快照并完成完整性校验。
- 单个 interactive transaction 获取 PostgreSQL advisory transaction lock，检查 `generatedAt` 单调性；当前快照 binding 查询及岗位更新、下架、活跃标记、创建均按管理端批次大小依次执行，全部批次成功后才原子推进成功快照时间。
- binding 仅加载“当前快照 ID”与“上次仍活跃”集合；当前 ID 按批次参数化查询，已关闭且本次未出现的历史 binding 不再加载。全量快照总数不限，每批默认 100 条、可配置 1-200 条。
- 差异字段通过 `jsonb_to_recordset` 参数化批量 SQL 更新；新岗位通过 `createMany` 创建，不按需求逐条往返。
- 最近岗位先用经纬度部分 B-tree 索引做自适应 bounding box 预筛选，再精算 Haversine；最后一级覆盖全球合法坐标，不能因候选截断漏岗。

## 部署核对

1. 两端配置同一个 `TUTOR_SYNC_TOKEN`；燚桐部署环境另设 `TUTOR_SYNC_ENABLED=true` 和可访问的 `TUTOR_SYNC_URL`。不需要审核 OpenID、claim 租约或容量环境变量。
2. 管理端进入“运营 -> 设置 -> 系统同步配置”，先设置每批同步数量，再开启“家教自动同步”。运行开关默认关闭，存入 `app_configs.tutor_sync.enabled`；只有它与部署环境的 `TUTOR_SYNC_ENABLED=true` 同时开启才会请求源接口。每批同步数量默认 100 条、可配置 1-200 条，存入兼容键 `app_configs.tutor_sync.max_demands`；该值不再限制全量总数。
3. 应用 Prisma migration 后，在隔离 PostgreSQL 执行 `EXPLAIN (ANALYZE, BUFFERS)`，确认 nearest 常见半径使用 `job_posts_nearest_location_lat_idx` / `job_posts_nearest_location_lng_idx`，并验证 advisory lock、事务回滚及唯一约束。
4. 在家教平台 PHP 运行环境执行语法检查，并用错误令牌、正确令牌分别验证 403 和完整快照响应。
5. 修改、关闭、删除一条测试需求，并对实际会改变 `status` 的退款流程做验证，确认下一轮同步后所有圈子的对应岗位更新或下架。当前生产表没有独立隐藏字段，不能以旧隐藏接口作为验收项。
