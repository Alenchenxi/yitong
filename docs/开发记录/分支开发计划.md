## 2. 各分支详细 brief

> 每条 brief 含：范围 / 涉及文件 / API（飞书《API设计规范》章节）/ 数据模型 / 依赖 / 暴露契约 / 完成标准 / 主要隐患。

### 2.1 `feat/chat` — TIM userSig 基建

- **范围**：封装腾讯云 IM（TIM）userSig 签发，供 merchant / job / treehole 复用。无独立 REST（按 API 规范 §6.4「站内沟通走 TIM，不经 REST，仅签发 userSig」）。
- **涉及文件**：`apps/server/src/modules/chat/tim.service.ts`、`chat.module.ts`（`@Global()`）。
- **API**：无 controller；提供 `TimService.signUserSig(identifier): { userSig, sdkAppId, expire }`。
- **数据模型**：无（TIM 侧账号由 identifier 标识）。
- **依赖**：auth（已在 main）；`TIM_SDK_APP_ID` / `TIM_SECRET_KEY` 环境变量。
- **暴露契约**：`TimService`（全局可注入）。消费方：merchant `POST /merchant/tim-sig`、job 站内沟通、treehole 匿名账号。
- **完成标准**：typecheck 通过；`signUserSig` 返回合法 userSig（缺凭证时 dev 返回 mock、prod 抛 90003，沿用 auth/common 的 mock 策略）；单测覆盖签名/过期。
- **隐患**：userSig 算法需用 TIM 官方 SDK 或 `@tencentcloud/user-sign`；expire 默认 7d；多实例无状态可签（无缓存需求）。

### 2.2 `feat/mp-confession` — 用户端·表白墙前端

- **范围**：用户端小程序接入登录态 + 表白墙四页（圈子 / 发帖 / 发现流 / 详情）+ 点赞评论交互。
- **涉及文件**：`apps/user-miniprogram/`（`app.ts` 登录态、`services/request.ts` 已有、`pages/confession/*`、`pages/post-detail/*`、`pages/post-create/*`、`components/post-card`）。
- **API**：飞书 §6.2（`GET /circles`、`POST /circles/:id/posts`、`GET /posts/feed`、`GET /posts/:id`、`POST /posts/:id/like`、`POST /posts/:id/comments`、`GET /posts/:id/comments`）+ `POST /uploads`（发帖带图）+ `POST /auth/wx-login` / `GET /auth/me`。
- **数据模型**：仅消费后端 VO（PostVo/CommentVo/FeedResult）。
- **依赖**：main（表白墙后端 + auth + upload 全部已就绪）。**无前置分支，立即可做。**
- **暴露契约**：无（纯前端）。
- **完成标准**：微信开发者工具跑通 登录→圈子→发帖(带图)→发现流→详情→点赞→评论 全链路（mock 后端）；mobx-miniprogram 登录态持久化；TDesign 组件接入；`tsc`/小程序构建无错。
- **隐患**：appid 占位（`touristappid`）需替换；图片上传走 `/uploads` 拿 URL 再发帖；游标分页「加载更多」交互。

### 2.3 `feat/merchant` — 商家入驻

- **范围**：商家入驻（资质 + 审核态）后端 + 商家端小程序入驻页 + `tim-sig` 签发。
- **涉及文件**：`apps/server/src/modules/merchant/{merchant.controller,merchant.service,merchant.module}.ts` + dto；`apps/merchant-miniprogram/`（入驻表单页）。
- **API**：飞书 §6.6（`POST /merchant/register`、`GET /merchant/profile`、`PATCH /merchant/profile`、`POST /merchant/tim-sig`）。
- **数据模型**：`Merchant`（shopName/licenseNo/contactPhone/status PENDING/APPROVED/REJECTED）。
- **依赖**：auth；chat（`TimService`，用于 tim-sig）。
- **暴露契约**：`Merchant` 模型 + `GET /merchant/profile`；job 分支依赖「商家已审核 APPROVED 才能发岗」。
- **完成标准**：typecheck + smoke（mock）：注册→profile→审核态流转；入驻表单页联调；`POST /merchant/tim-sig` 返回 userSig。
- **隐患**：资质图片走 `/uploads`；营业执照号格式校验；审核态由 admin 分支控制（此处只建 PENDING）。

### 2.4 `feat/job` — 兼职岗位 / 报名 / 评价

- **范围**：岗位草稿/列表/详情 + 报名(防重) + 状态流转(accept/complete) + 评价；用户端兼职页 + 商家端发岗/报名管理。
- **涉及文件**：`apps/server/src/modules/job/*` + dto；`apps/user-miniprogram/pages/job/*`；`apps/merchant-miniprogram/pages/job/*`。
- **API**：飞书 §6.4（`GET /job-posts`、`GET /job-posts/:id`、`POST /job-posts`(草稿)、`POST /job-posts/:id/applications`、`GET /job-posts/:id/applications`、`PATCH /applications/:id`、`POST /applications/:id/review`）+ §7.2 状态流转。
- **数据模型**：`JobPost`（status PENDING/PUBLISHED/TAKEN_DOWN/EXPIRED，duration D30/D90，expireAt）、`JobApplication`（`@@unique([jobPostId,userId])` 防重）、`JobReview`。
- **依赖**：merchant 契约（JobPost.merchantId = 已审核 Merchant）；moderation（岗位描述 checkText）；chat（站内沟通 userSig，可选先 stub）。
- **暴露契约**：`JobPost` 模型 + `POST /job-posts` 返回草稿 id；**payment 分支依赖此**（付费发布订单关联 jobPostId）。
- **完成标准**：typecheck + smoke（mock）：商家发草稿→用户浏览→报名(防重 409)→商家录用→标记完成→评价(1-5 星)；非法流转返 40004；用户端/商家端联调。
- **隐患**：草稿为 PENDING，**PUBLISHED 由 payment 回调置位**（跨分支契约，见 §4）；状态机非法流转统一 40004；评价只能一次（JobReview applicationId 唯一）。

### 2.5 `feat/payment` — 付费发布 + 微信支付

- **范围**：按 `PricingConfig` 计价下单 + 微信支付下单 + 回调验签 + 置岗位 PUBLISHED + 设 expireAt。
- **涉及文件**：`apps/server/src/modules/payment/*` + dto；`apps/merchant-miniprogram/pages/payment/*`。
- **API**：飞书 §6.5（`POST /payments/job-publish`、`POST /payments/notify`）+ §7.1 付费发布流程。
- **数据模型**：`PricingConfig`（duration 唯一，price Decimal）、`PaymentOrder`（wxPrepayId/status PAID…）。
- **依赖**：job 契约（JobPost.id + duration）；merchant。微信支付商户号/证书/V3 key。
- **暴露契约**：`POST /payments/notify` 验签后 **写 JobPost.status=PUBLISHED + expireAt**（跨分支写 job 的表，见 §4）。
- **完成标准**：typecheck + smoke（mock 支付：dev 跳过真实拉起，直接置 PAID→PUBLISHED 验证状态机）；金额服务端按 PricingConfig 算（不信前端）；回调验签逻辑就绪（缺凭证 mock）。
- **隐患**：金额必须服务端算；回调幂等（同一 prepayId 重复回调不重复置位）；expireAt = now + 30/90 天；真实支付需商户证书，dev 走 mock 通路。

### 2.6 `feat/treehole` — 树洞匿名动态 + 匹配聊天

- **范围**：匿名态签发(独立身份) + 匿名动态广场 CRUD + 随机匹配(Redis 队列) + TIM 匿名账号 1v1 文字聊；用户端树洞页。
- **涉及文件**：`apps/server/src/modules/treehole/*` + dto；`apps/user-miniprogram/pages/treehole/*`。
- **API**：飞书 §4.2 + §6.3（`POST /treehole/anonymous-token`、`POST /treehole/posts`、`GET /treehole/posts`、`POST /treehole/match`、`POST /treehole/chats/:id/messages`）。
- **数据模型**：`AnonymousProfile`（userId↔anonId，**后台可追溯、前台不暴露**）、`AnonymousPost`（仅 anonId，**禁落真实 uid**）、`ChatMatch`（anonIdA/B）。
- **依赖**：auth（anonymous-token 需登录换发）；chat（匿名账号 userSig）；moderation（匿名帖 checkText/checkImage）；Redis（匹配队列）。
- **暴露契约**：匿名 token 体系；不向其他分支暴露真实身份映射。
- **完成标准**：typecheck + smoke（mock）：登录→换匿名 token→发匿名帖→广场→匹配→1v1 聊天；**树洞表 0 处真实 uid**（代码审查 + 断言）；Redis 缺失时匹配降级排队。
- **隐患**：**匿名隔离是红线**——anonToken 不得含 uid、AnonymousPost 不得存 userId；匹配用 Redis 队列（BLPOP/LPUSH）或内存降级；MVP 砍兴趣匹配/历史会话/匿名点赞（roadmap 已降 P1）。

### 2.7 `feat/admin` — 管理端 Web + 审核

- **范围**：管理端 Vue3+Element+Vite 登录 + 审核队列(表白墙/树洞/岗位/商家) + PricingConfig 单价配置 + 用户封禁。
- **涉及文件**：`apps/admin-web/`（新 scaffold：Vue3+Vite+Element Plus+Pinia+axios）；`apps/server/src/modules/admin/*` + `moderation` 审核接口。
- **API**：飞书 §4.3 + §6.7（`POST /admin/login`、`GET /admin/moderation/queue`、`PATCH /admin/moderation/:id`、`GET /admin/merchants`、`PATCH /admin/merchants/:id`、`GET /admin/pricing`、`PATCH /admin/pricing`、`PATCH /admin/users/:id/ban`）。
- **数据模型**：`AdminUser`（username/passwordHash）、`ModerationRecord`、`PricingConfig`、各内容表 status。
- **依赖**：各内容模块契约（审核读 Post/AnonymousPost/JobPost/Merchant）；建议在 confession/job/treehole/merchant 合并后做，但可先按契约 scaffold。
- **暴露契约**：`@AdminGuard` + admin token；PricingConfig 写入供 payment 读取。
- **完成标准**：typecheck + admin web 构建；登录→审核队列(通过/拒绝)→商家审核→单价配置→封禁 全链路；admin login 用 `AdminUser`（非 wx）。
- **隐患**：admin 密码 bcrypt；IP 白名单（API 规范 §4.3）；审核动作要回写各内容表 status（跨模块写，见 §4）。

### 2.8 `feat/cron-deploy` — 到期下架 + 部署

- **范围**：岗位到期下架定时任务 + 后端部署配置。
- **涉及文件**：`apps/server/src/modules/job/job.scheduler.ts`（或 `common/cron`）；`Dockerfile`、`ecosystem.config.js`(PM2)、`nginx.conf` 示例、`docs/开发记录/部署.md`。
- **API**：无新接口。
- **数据模型**：读 `JobPost`（PUBLISHED + expireAt<now → EXPIRED）。
- **依赖**：job（JobPost 模型）。
- **暴露契约**：无。
- **完成标准**：cron 单测（构造过期岗位→触发→状态 EXPIRED）；Dockerfile 构建 server 镜像通过；PM2/Nginx 配置就绪（可不实际部署，配置正确即可）。
- **隐患**：cron 单实例（多实例需分布式锁，避免重复下架）；时区（expireAt 用 UTC，比对注意）。

## 3. 依赖与合并顺序（DAG）

```
main 基线: auth + common + confession-backend
        │
        ├── W0  feat/chat  ──────────────── (共享基建，最先合并)
        │
        ├── W1 (可并行，全部从 main 切出)
        │     ├── feat/mp-confession   (无前置)
        │     ├── feat/merchant        (auth)
        │     ├── feat/job             (merchant 契约 / moderation)
        │     └── (feat/treehole 需 chat，可在 chat 合并后并入 W1 末或 W2 初)
        │
        ├── W2 (依赖 W1)
        │     ├── feat/payment         (job 契约)
        │     └── feat/treehole        (chat)
        │
        └── W3 (依赖内容模块)
              ├── feat/admin           (各内容模块)
              └── feat/cron-deploy     (job)
```

- **起始**：所有分支可同时开工（按飞书契约编码，消费方对未合并依赖先 stub/mock）。
- **合并 gating**：`chat` 先进 main → `treehole`/`merchant`/`job` → `payment` → `admin`/`cron-deploy`。每条合并前必须过 §6 测试门槛。
- **rebase**：合并一条后，其余分支 `git rebase main` 拉取最新（尤其 schema.prisma / app.module.ts 变更）。

## 4. 分支协同契约（跨分支读写约定）

| 写方 | 读/写 | 对方表/接口 | 约定 |
|-|-|-|-|
| `feat/job` | 写 | `JobPost` 草稿(PENDING) | 草稿由 job 创建，status 停在 PENDING |
| `feat/payment` | 写 | `JobPost.status`→PUBLISHED + `expireAt` | 回调验签后置位；**不重复置位**（幂等） |
| `feat/cron-deploy` | 写 | `JobPost.status`→EXPIRED | 扫 PUBLISHED+expireAt<now |
| `feat/admin` | 写 | 各内容表 status + `ModerationRecord` | 审核「拒绝」回写 REJECTED |
| `feat/merchant` | 读 | `Merchant.status` | job 发岗前校验商家 APPROVED |
| `feat/chat` | 提供 | `TimService` | merchant/job/treehole 注入调用 |
| `feat/treehole` | 隔离 | `AnonymousProfile`↔`User` | **真实 uid 仅后台可追溯，前台/匿名 token 0 暴露** |

> 跨分支写同一张表（如 JobPost 被 job/payment/cron/admin 都写）时，**各写不同 status 流转分支**，互不重叠字段，冲突可解。

## 5. 共享文件冲突协议

并行分支易在以下文件冲突，按协议处理：

- **`apps/server/prisma/schema.prisma`**：每模块只加自己的 model（数据模型已设计好归属）。迁移各自 `prisma migrate dev --name <module>`。合并时按迁移时间顺序保留全部；冲突手动物理合并 model 列表。**新迁移必须可重放。**
- **`apps/server/src/app.module.ts`**：每分支只加自己的 `imports` 一行；合并取并集。
- **`docs/开发记录/改动记录.md`**：每分支在顶部追加自己的条目（格式见现有）；合并时按时间戳交错，保留全部。
- **`apps/server/package.json` / `pnpm-lock.yaml`**：每分支加自己依赖；合并取并集后 `pnpm install` 重生成 lock。
- **`apps/user-miniprogram/app.json`**：新增页面注册到 `pages`；合并取并集。

## 6. 工作流与测试门槛（每条分支）

1. **切分支**：`git checkout main && git pull && git checkout -b feat/<name>`（本地 main 含 `63639b5`）。
2. **开发**：按本 brief + 飞书契约实现；mock 策略沿用 auth/common（缺凭证 dev mock、prod 抛错）。
3. **本地测试门槛（必须全过才能合并）**：
   - `pnpm -C apps/server run typecheck`（或对应端 typecheck/构建）通过；
   - 端到端 smoke（mock 模式）跑通核心链路（参考 confession 的 smoke 脚本）；
   - 关键单测（状态机/防重/匿名隔离等 P0 逻辑）；
   - 涉及 schema 的分支：`prisma migrate dev` 成功 + 必要时 `prisma db seed`。
4. **同步改动记录**：在 `docs/开发记录/改动记录.md` 顶部追加一条（字段顺序：发生时间→状态→commit→改动概要→新增/修改文件→完成的工作→潜在隐患→后续待做工作/方向），格式与现有条目一致。
5. **合并**：`git checkout main && git merge --squash feat/<name> && git commit`（Conventional Commits，中文 subject + `Co-Authored-By`）；合并后 `git push origin main`（网络不稳时多重试，或用户 `! git push`）。
6. **通知**：合并后告知其他分支 rebase main。

## 7. 风险与注意事项

- **GitHub 推送不稳**：本机到 github.com:443 频繁超时/重置（errno 10054 / Timed out）。`63639b5` 已是本地未推送状态；各分支合并后推送可能需多重试或走代理。
- **mock 掩盖真实路径**：auth/common/confession 均为 mock 模式下验证，真实 WX/COS/TIM/支付凭证需在部署前配齐并回归。
- **匿名隔离红线**：treehole 必须在代码审查 + 断言层面保证「树洞表 0 真实 uid、anonToken 不含 uid」。
- **跨分支状态机**：JobPost.status 由 4 个分支共同流转，务必按 §4 约定各管一段，合并后做一次端到端状态机联调。
- **并行合并顺序**：严格按 §3 波次，避免 payment 在 job 合并前并入造成 JobPost 字段缺失。
- **行尾**：Windows 下 LF/CRLF 警告，建议尽快加 `.gitattributes`（`* text=auto eol=lf`），可由任一分支顺带处理。
