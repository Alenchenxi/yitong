## 3. 变更详情

### 技术变更

- **入参**：`backupHotel`，可选，去首尾空格后最长 40 字符。
- **校验**（在短信校验之前，失败不触达飞书）：
  - 填了但不在酒店列表、或与报名酒店相同 → 400「备选酒店无效，请重新选择」
  - 填了但该酒店已暂停报名 → 400「备选酒店已暂停报名，请重新选择」
- **写入前的列准备**：
  - 填了备选 → 确认「备选酒店」列存在，不存在则新增文本列（`POST /fields`，`type: 1`），再把备选和报名字段放进同一次记录写入。
  - 重复提交且未填 → 列已存在时，在同一次写入里把它置为空字符串；列不存在则不写这个字段。
  - 首次报名且未填 → 不查列、不建列、不写该字段。
  - 「列是否存在」的结论在进程内缓存；记录写入失败时清掉缓存，下次提交重新确认并补建，应对列被改名或删除。
- **降级**：列的存在性检查或新增失败时，报名照常写入并返回成功，只是不带备选，同时记录错误日志（含手机号与备选酒店名）。一列可选字段不能拖垮报名。
- **前端**：`openForm(h)` 每次打开都重建下拉，选项为 `HOTELS` 中 `name !== h.name` 且未暂停的酒店，默认项「不填」。

### 已知限制

- 飞书「新增字段」接口没有位置参数，程序建出的列排在最右侧。要放到「报名酒店」后面，需要在飞书里手动拖一次；也可以提前手动建好该列，程序检测到已存在就直接写入。
- 自动建列要求应用具备 `base:field:create` 或 `bitable:app` 权限。缺失时走降级（报名成功、备选未写入），补权限或手动建列后恢复。

## 4. 增量任务

每个任务按 TDD 循环执行：RED → GREEN → REFACTOR。

### 后端

#### [x] Task-CR006-01：/api/apply 接收备选酒店并与报名一次写入飞书

**通俗解释**：填了备选酒店，飞书那一行的备选格和报名信息一起写进去；列还没建就先建列。备选这列出任何问题，都不能让报名本身失败。

**做什么**：
1. RED：新增 `tools/feishu-stub.js`（`node --require` 预加载，把 `fetch` 对飞书的请求替换成可控桩，并把调用序列写进日志文件）和 `test/backup-hotel.test.js`，覆盖写入时序：
   1. 列已存在 + 新报名带备选 → 不建列，记录只写一次且含「备选酒店」
   2. 列不存在 + 带备选 → 先新增文本列（`type: 1`）再写入
   3. 新报名不带备选 → 没有任何列操作，写入不含该字段
   4. 重复提交不带备选、列已存在 → 更新时该字段写空字符串
   5. 建列失败 → 仍返回成功，写入不含该字段
   6. 备选与报名酒店相同或不存在 → 400 且没有记录写入
   7. 重复提交不带备选、列不存在 → 不会为了清空而建列，更新不含该字段
   8. 带备选的写入因列被删而失败 → 下次提交重新确认并补建列后成功
2. GREEN：在 `handleApply` 中实现入参解析、校验、列准备、同次写入与降级。
3. `test/server-contract.test.js` 加一条静态断言：备选酒店已暂停时被拒绝（桩环境的配置里没有暂停酒店，行为测试覆盖不到）。
4. `AGENTS.md` 红线补一行：飞书「备选酒店」为文本列，由程序自动新增、排在最右需手动调整位置；重复提交未填即清空。

**涉及文件**：`src/app.js`、`test/backup-hotel.test.js`、`tools/feishu-stub.js`、`test/server-contract.test.js`、`AGENTS.md`

**参考**：AC-021、AC-022、AC-023、AC-024；本文档「技术变更」

**依赖**：无

**预估工时**：60 分钟

**验证标准**（TDD RED 阶段依据）：
- [x] 八条行为用例断言飞书调用顺序、建列参数与写入字段。其中「不带备选的新报名」一条是回归基线，改动前即通过；其余七条先失败后通过
- [x] 不带备选的报名，飞书调用序列与改动前完全一致
- [x] 建列失败时响应仍为 `ok: true`

**实现补充**：行为测试把 `src/`、`config/` 逐文件拷到临时目录再起服务。原因是本地 `.env` 配了真实的飞书和短信参数，原地起服务会启用验证码校验，也有误写真实表格的风险。
