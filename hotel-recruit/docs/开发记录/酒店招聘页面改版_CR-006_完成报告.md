## 问题与决策

### 改为一次写入

**情况**：规划初稿是「先写报名，再单独补写备选」，这样备选出错时天然不会影响报名。用户要求两者必须一起写入。
**处理**：改成写入前先确认列存在（没有就建），再把备选放进同一次记录写入。隔离性改由两处兜底保证：列的检查或新增失败时降级为不带备选；带备选的写入失败时清掉「列已存在」缓存，下次提交自动重新确认并补建。
**影响**：备选列不存在且要写备选时，首次请求多一次查列和一次建列；之后进程内不再查。

### 本地 .env 配了真实参数

**情况**：`hotel-recruit/.env` 里是真实的飞书和短信配置，本地原地起服务会启用验证码校验，也有误写真实表格的风险。
**处理**：行为测试和浏览器验收都把 `src/`、`config/`（验收另加 `public/`）拷到临时目录再起服务，飞书请求全部由桩接管。
**影响**：以后在本地调试这个项目，起服务时必须显式覆盖 `APP_ID` 等环境变量，且不要调用 `/api/apply`、`/api/sms/send`。

### fs.cpSync 递归拷贝会让进程异常退出

**情况**：本机 Node 24.11 上 `fs.cpSync(dir, dest, { recursive: true })` 执行后进程被硬终止，退出码 127，没有任何报错输出。
**处理**：测试里改为逐文件 `copyFileSync`。
**影响**：本机其他脚本遇到同类现象可按此绕开。

### 桩文件放在 tools/ 而不是 test/

**情况**：`node --test` 默认会把 `test/` 目录下所有 JS 当成测试文件，桩放在 `test/helpers/` 会多出一条恒通过的假用例。
**处理**：挪到 `tools/feishu-stub.js`。

## 技术债务

- **列的位置要手动调**：飞书「新增字段」接口没有位置参数，程序建出的列在最右侧，需在飞书里拖到「报名酒店」后面；各视图的列顺序分别调整。
- **建列权限未验证**：自动建列要求应用有 `base:field:create` 或 `bitable:app` 权限。缺失时报名照常成功但备选不入表，只留 `[backup]` 日志，直到补权限或手动建列。建议上线后尽早做一次线上验收来确认。
- **首次建列的并发竞态**：两人几乎同时成为第一批填备选的报名者时，后到的那次建列会报「字段名重复」，该请求降级为不带备选并记日志。窗口极小，未做处理。
- **列不存在时的重复查列**：列还没建出来之前，每次「重复提交且未填备选」都会多查一次列；列建出来后进程内不再查。
- **浏览器验收没有自动化**：本机没有 Playwright，这次用 Edge 无头模式加临时探针页完成，探针页未入库。
